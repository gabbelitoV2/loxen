## Device motion, attitude and accelerometer (MOTION, package com.moblin.android.platform.coremotion)
- `CMMotionManager()`, `deviceMotionUpdateInterval`, `stopDeviceMotionUpdates()` keep their shape; `startDeviceMotionUpdates(to: OperationQueue.main) { data, _ in }` -> `startDeviceMotionUpdates(to = OperationQueue.main) { data, _ -> }`. `OperationQueue.main` runs the handler on the main thread; the handler never runs after `stopDeviceMotionUpdates()`, which unregisters the sensors.
- `data.attitude` is a `CMAttitude` with `roll`, `pitch` and `yaw` (radians, iOS axes and Euler order, yaw from an arbitrary start) and `quaternion` (`CMQuaternion` x, y, z, w). A stored `CMAttitude?` keeps its type, never `Any?`. There is no `rotationMatrix` or `multiply(byInverseOf:)`.
- `accelerometerUpdateInterval`, `stopAccelerometerUpdates()`, `isAccelerometerActive` and `accelerometerData` keep their shape; `startAccelerometerUpdates(to: .main) { data, error in }` -> `startAccelerometerUpdates(to = OperationQueue.main) { data, error -> }`, and `guard let data, error == nil else { return }` -> `if (data == null || error != null) { return@startAccelerometerUpdates }`. `data.acceleration` is a `CMAcceleration` (x, y, z `Double` in g, iOS axes, gravity included, so about 1 at rest), never m/s^2 from `android.hardware.SensorManager`.
- One `CMMotionManager` runs device motion and accelerometer updates side by side, and stopping one keeps the other, like iOS. Model's `private let motionManager = CMMotionManager()` -> `private val motionManager = CMMotionManager()`, used by `startMotionDetection`, `stopMotionDetection` and `GForceManager(motionManager = motionManager)`; `GForceManager(motionManager: CMMotionManager)` keeps that parameter.
